> [!answer]- 派生自查口径（首答后展开）
> 核心机制：机器字长与 ALU、通用寄存器、指令寄存器、浮点寄存器宽度的关系；n 位 CPU 的口径落在机器字长或整数数据通路宽度，不能与地址总线位数混同；通用寄存器宽度通常与机器字长和整数数据通路一致，不由存储容量或指令长度直接决定
>
> 达标标准：
> - CO_2020_001 知识点：CO01-17 机器字长
> - CO_2020_001 安全摘要：概念判断题，要求区分机器字长通常反映整数数据通路宽度和通用寄存器宽度，但不应无条件套到所有寄存器或指令相关宽度上。
> - CO_2020_001 关键参数核验：机器字长、ALU 位数、通用寄存器位数、指令字长、指令寄存器宽度、浮点寄存器宽度；判断时要区分“通常相关”和“必然相等”。
> - CO_2020_001 错误入口核验：曾误以为 ALU 位数不一定等于机器字长，又把指令寄存器、浮点寄存器也默认看成与机器字长相同。
> - CO_2020_001 第一动作核验：先写机器字长定义，再分三类判断：整数数据通路相关、指令存储/取指相关、专用/扩展寄存器相关。
> - CO_2020_001 机制边界：机器字长与 ALU、通用寄存器、指令寄存器、浮点寄存器宽度的关系
> - CO_UNK_022 知识点：CO01-17 机器字长
> - CO_UNK_022 安全摘要：围绕“所谓 n 位 CPU 中 n 的含义”做概念辨析，需要区分 CPU 数据处理宽度、寻址范围和控制信号数量。
> - CO_UNK_022 关键参数核验：候选口径包含地址相关线数、数据相关宽度、控制相关线数和 I/O 相关线数；题眼是 CPU 一次处理/传输数据的口径，不是外部数量的机械相加。
> - CO_UNK_022 错误入口核验：历史归档未记录明确错因；高风险入口是把 CPU 位数和地址总线/控制线/I-O 线数量混为一谈。
> - CO_UNK_022 第一动作核验：先问“这个位数描述的是数据处理宽度、寻址范围还是控制信号数量”，再比较候选口径。
> - CO_UNK_022 机制边界：n 位 CPU 的口径落在机器字长或整数数据通路宽度，不能与地址总线位数混同
> - CO_UNK_026 知识点：CO01-17 机器字长
> - CO_UNK_026 安全摘要：围绕 CPU 中通用寄存器位数由哪类硬件口径决定进行辨析，重点排除主存容量和指令长度等相邻概念。
> - CO_UNK_026 关键参数核验：候选维度包含存储容量、指令长度、CPU 一次处理数据的宽度及兜底项；需要判断通用寄存器服务于数据通路还是服务于寻址容量/指令编码。
> - CO_UNK_026 错误入口核验：视觉卡显示曾把存储容量当成决定因素，说明没有先把寄存器宽度与 CPU 数据处理口径绑定。
> - CO_UNK_026 第一动作核验：先问“这个寄存器参与数据运算还是描述存储空间/指令编码”，再把候选因素逐一归类。
> - CO_UNK_026 机制边界：通用寄存器宽度通常与机器字长和整数数据通路一致，不由存储容量或指令长度直接决定
